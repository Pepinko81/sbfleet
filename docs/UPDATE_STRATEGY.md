# Explicit pinned update

> **STATUS:** Apply uses private staging + source-pin official `update.sh`, fresh recovery-verified pre-update backup inside the UPDATE lock, **full updater-owned staged vendor surface bind to the approved `to_sha` snapshot**, **operation-scoped canonical promote-record** (exact pre/target path type/state/hash + durable per-path progress; journal pointer/summary may lag after process death), mechanical promotion of an approved staged result, post-promote `verify_deployment_vendor` before `run.sh pull`, and runtime verification before `last_verified_upstream` advances. Interrupted updates continue via `update --reconcile --operation-id` on the **same** operation (no new backup/replan/edge). Only explicitly reviewed directed edges (currently `self-hosted/v0.8.1` → `self-hosted/v0.8.2`) are supported.

## Contract

`update P --to self-hosted/vX.Y.Z --dry-run` is a plan; without --dry-run it is a maintenance operation requiring --yes or interactive acknowledgement. No implicit latest, background updates, downgrades, arbitrary branches or unreviewed PostgreSQL major upgrades. Same verified ref is a validated no-op.

**Recovery after interruption is phase-dependent:**
- **No promotion began** (promote-record present; live still exact source): unresolved journal still blocks ordinary restore/update; after explicit `--reconcile` / journal resolution, same-pin restore of the pre-update archive may apply while destination pin still matches the archive.
- **Partial / complete promotion** (mixed or target tree; metadata may already show target pin): pre-update archive remains valuable evidence/data protection; **direct same-pin restore into a promoted different-pin destination is unsupported**; use `--reconcile` when staging can be rebound to the approved target; otherwise diagnose-only. sbfleet does **not** claim generic cross-version rollback.
- Do **not** advise blind “retry update” or “restore pre-update backup” while gates necessarily refuse those operations.

Project metadata tracks desired/current vendor ref and exact SHA separately from last_verified_upstream. `.supabase-version` is upstream's merge-base state, not a health claim. Journal tracks phases; the **canonical** crash truth is the operation-scoped promote-record. A crash after vendor promotion must be distinguishable from successful update.

## Planning without deployment writes

Under project lock validate current metadata/stamp/vendor checksums and service ownership. Fetch requested stable official tag to cache, resolve commit and record SHA. Reject tag moves against known pin. Compare exact old/new service/mount/port/PG image structure through compatibility adapters. New unknown shape is BLOCKED_ARCHITECTURE for implementers and unsupported update for operators. Read target upgrades.json; any breaking/gate entry or PG major change is refused in automated V1, with upstream manual instructions. --yes never bypasses this. Minor supported same-shape upgrades are V1; no false claim of supporting arbitrary future releases.

Make a private **configuration-only** staging tree, no live data bind directories, no symlinks into deployment. Place old .env and stamp there, invoke old pinned `sh update.sh --to TARGET --dry-run` with sanitized official SUPABASE_REPO_URL and captured output. Dry-run may exit 0 despite conflicts; independently inspect staged merge behavior or parse bounded known-version report, don't use exit code alone. Plan lists image/config diffs by name (not secret values), new .env key names, override compatibility, downtime, exact backup prerequisites, disk requirements and blockers. No .env/source/metadata mutations. Cache writes are allowed and disclosed.

## Apply ordering

1. Revalidate plan/ref/SHA/current state under lock; no stale-plan execution. Require current stack healthy (or a previously stopped but valid project that can be temporarily started for prerequisite checks with explicit maintenance consent).
2. Perform BACKUP_RESTORE's encrypted, fully verified pre-update backup, including all DBs, Storage and keys. If any step or restart fails, STOP. Record backup ID. No --skip-backup.
3. Keep the project in maintenance with all services stopped. Do not allow writes after the recovery point and before configuration change. The backup helper supports returning quiesced to its update caller instead of restarting. Record prior running state.
4. In private config staging, invoke official old `sh update.sh --to TARGET` (stdin closed). V1 already rejected manual gates; do not supply upstream --yes blindly. It performs its own config tar/merge/stamp there, not against live deployment. Its tar can contain plaintext .env: keep 0700 staging; delete after encrypted diagnostic retention. Verify exit, conflict markers, expected vendor hashes, .env key preservation and all new required keys. Unresolved/default secret values fail; never rerun whole key-generation scripts on an existing deployment.
5. If update.sh.dist exists, refuse (updater self-update requires manual reconciliation). No ad-hoc downloaded script. Enforce target ref↔SHA (`to_sha` is a fact). **Bind the complete updater-owned staged vendor surface** to the independently materialized approved target snapshot at `to_sha` (expected files, additions, removals, types, hashes). Exclude only the closed fleet/generated/runtime ownership boundary (override, `.env`, `.sbfleet-upstream`, sbfleet-copied root `LICENSE` attribution, data volumes, backups, staging leftovers, etc.) — not an expanding preserve list. Reject unexpected staged upstream-owned bytes and removed-upstream leftovers. Critical-cache digest match alone is insufficient.
6. Generate fleet override anew, explicitly restore COMPOSE_FILE/name, validate effective config and preserve .env secrets. Stage validation uses dummy/private paths without mounting live data. Preserve live mutable functions/snippets per upstream ignore policy; vendor function main/index.ts follows upstream update semantics. Archive old config encrypted.
7. Persist operation-scoped promote-record (intended path states) **before** first live mutation; journal may only pointer/summarize afterward. Promote vendor/config files with atomic individual replaces while stopped; exclude runtime data and fleet metadata; verify type/state/hash before recording path `verified`. No claim of atomic whole-tree swap. Update metadata vendor ref/SHA; last_verified remains old. **Re-verify deployment critical vendor digests against the approved target cache before any promoted script runs.**
8. Run project-local `sh run.sh pull`, record digest resolution, then `sh run.sh start --wait-timeout ...` (already stopped; equivalent to recreate without redundant down). Validate isolation, all health, authenticated Studio and gateway/API probes. Preserve prior STOPPED state by stopping again after successful verification when appropriate. Only then advance last_verified and report UPDATED.

## Failures

Any merge, secret, pin, port, pull or health failure is nonzero. Leave gateway stopped on failed new runtime verification; retain journal, promote-record, encrypted old config, backup ID and version discrepancy. Do not retry blindly, regenerate keys or downgrade DB images. doctor identifies staged vs applied vs last verified refs and points at `update --reconcile --operation-id`. Reconcile continues the same operation from the canonical promote-record (no new backup/replan). Same-pin restore of the pre-update archive applies only while destination pin still matches; after promotion that path is unsupported. Irreversible data/service migrations have no automatic rollback promise.

Unit/process tests cover dry-run exit-0 conflicts, upstream exit 2, missing/new secret defaults, mutated tags, .dist, backup failure, partial promotion / SIGKILL promote-record durability, pull failure and post-start health failure. Real update acceptance uses two compatible official pins or a same-ref no-op plus fault injections; record exactly which was exercised, never call no-op a real version transition. If a second supported official target is unavailable, the transition gate remains WAITING_EXTERNAL.
